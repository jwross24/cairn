# Own view — guard round 6 (written before opening any seat file)

Plan read: plan-r5.md in full. Five most likely demonstrable defects, ranked.

1. **§3 checkpoint verifies only "the last checkpoint" (MED, mechanism).** The chain head is appended "at every gate run" to an append-only file the orchestrator's process user can extend, and the verification rule is "a log that does not extend the last checkpoint fails verification". A party with the process user's powers (the raw-write path the checkpoint exists to guard) can truncate the log to an earlier valid prefix, append forged records, and at the next gate run legitimately append the forked head to the checkpoint; the log then extends the last checkpoint and verification passes, while the older checkpointed head is orphaned and nothing checks it. The purpose sentence ("truncation to an earlier valid prefix is the one edit a hash chain cannot see") is not delivered by the check as written. Fix: the log must extend every checkpointed head (each is a prefix head of the current chain), not only the last; M2 done-when gets the fork fixture.

2. **§5 "the ladder's distribution rungs (≤ 50 bits) are Tier-1" vs §6 "each rung's tier follows its declared cost profile under the chosen count (an interpreted 50-bit baseline at that count runs for hours...)" (MED, contradiction).** If the boundary table assigns a ≤ 50-bit rung Tier 2, the ticket lattice has no ticket for it: Tier-2's algorithmic ticket is KEEP, and KEEP_IN_SAMPLE admits only the 60-bit rung. The fix names which governs: the ladder plan is sized at M1 so each ≤ 50-bit rung sits in Tier 1 under the boundary table, and a rung the table assigns Tier 2 is a ladder-plan error that refuses to start.

3. **§6 ladder sandbox for the method under test does not name network egress or wall-clock (MED/LOW, gaming path).** The allow-list forbids other arithmetic backends and process spawn; CPU time over the process tree is checked against counted ops. A method that opens a socket to a remote solver has near-zero counted ops and near-zero CPU time and passes the clock check; neither the counter nor the clock sees remote compute. One closing line: no network egress on the ladder's allow-list, and wall-clock exceeding CPU time beyond the plan's tolerance marks the rung INCONCLUSIVE (an idle wait on a remote call is visible to the wall clock).

4. **Submission verifier input binding (LOW/MED, gaming path).** §13 describes the verifier as a subprocess with decimal-string inputs (curve, n, P, Q, x) and §10 makes its passing node the only submission. Nothing says the curve, n, P and Q come from the claim statement node (or the ladder's dispatch record) rather than from the submitter. A worker that submits its own (P, Q' = x'P, x') satisfies the letter. Closing line: the gate run reads the instance from the statement node or dispatch record, the submitter supplies x alone, and the passing node records the instance it verified.

5. **Build-order and wording nits (LOW).** (a) M1 writes ledger entries (a ladder REJECT "writes" an entry; fixture (b) writes an `implementation` entry; KILLED "writes the ledger entry of §4") while "Dead-end ledger" is an M2 deliverable; the entry schema must land with the ladder at M1 and M2 adds the preflight. (b) §5 "the gate reads five launch-supplied inputs and no others" but also evaluates the profile "at the launch's inputs" and compares "declared purpose" against a KEEP_IN_SAMPLE ticket — six or seven inputs. (c) The `Leaked` record is "counted and escalated" with no named consumer in production (no human-queue class, no orchestrator tick rule). (d) The sorted-distribution shape diagnostic "surfaces on the human queue" but §10's queue classes name no class for it.

Ceremony suspects: `Leaked` (no production consumer named), the shape-diagnostic column (human-only, no class, no retirement condition), `caught_by` (printed, never branched on — a column, cheap, keep).
