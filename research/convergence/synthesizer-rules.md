# Synthesizer rules (one fresh Fable agent per round)

Inputs: the plan under review for this round; the seat reviews for this round (four OpenRouter seats + one grounded seat); all prior ledgers; the rules below. Output: the next plan file and a ledger. PLAN.md itself is never written by the synthesizer.

1. Form your own view first. Before opening any seat review, read the plan and write the five weaknesses you consider most important to `own-view-r{N}.md`. This is the anti-anchoring step; it is compared against the seats afterward, not merged blindly.
2. Dedupe the seats into clusters. For each cluster record: title · section · severity (HIGH structural / MED mechanism / LOW wording, re-judged by you, not copied) · which seats raised it (consensus count) · disposition ACCEPT / ACCEPT-PARTIAL / REJECT · cause.
3. Invariants are not revisable. Any proposal that weakens §0, the gate layer's existence or immutability, the calibration taxonomy, the ladder, the verifier, the no-go checklist, or the honest baseline is REJECTED and listed under "flagged invariant attacks", whatever its severity or consensus.
4. New mechanisms must pass the adoption bar (named component · cost · evidence tag and where · does not let strategy edit truth). No home ⇒ REJECT as homeless cleverness.
5. Evidence-check before accepting. A factual claim by a seat (a tool behavior, a number, a coverage claim, "X is standard") is checked against research/PROPOSALS.md, research/briefs/, research/grounding/ and HANDOFF.md; cite the file:line you checked. A seat claim that does not reproduce is annotated in the ledger and not integrated. The grounded seat can be wrong too.
6. Never re-litigate. A cluster matching a prior round's REJECT is rejected again unless the seat brings new evidence; say which prior ledger entry it repeats.
7. Operator defaults stand unless a seat gives a concrete, evidenced reason: the name Cairn; Sage/PARI backend; toy-curve M0 exemplar; SQLite + BLAKE3; Lean 4 + mathlib.
8. Accept only what improves the plan for a fresh implementer: sharper contracts, missing failure modes, contradictions resolved, self-containment, justified whys. Reject churn: renames for taste, restructurings that move text without adding information, and anything that makes a section less self-contained or deletes a "why".
9. Integrate in place, meticulously. Write the new plan to `plan-r{N}.md`: keep section numbering (CLAUDE.md and HANDOFF.md cite §0, §7, §13 …); keep the v2 sentences that are still true; write timeless prose inside the plan (state what the system does; never "now", "no longer", "previously", "this change", "instead of" as change narration); American spelling; every accepted mechanism keeps or gains a one-sentence "why".
10. Validation loop on the new plan, recorded in the ledger: (a) self-containment — pick the most obscure M0 task and say whether it is implementable as written; (b) dependency sanity — milestones and their "done when" form a DAG with no orphan mechanism (every mechanism is built in some milestone); (c) justification sampling — five decisions, each has a why; (d) steady-state diff — one paragraph on how structural this round's diff is versus the previous plan.
11. Verdict. `steady = STEADY` iff the maximum severity among ACCEPTED changes is LOW (or nothing was accepted) AND no factual correction changed a mechanism; otherwise `NEEDS-ANOTHER-ROUND`. State the expected residual scope for the next round in one sentence.
12. Ledger. Write `ledger-r{N}.md` (human-readable: accepted with severity/seats/section; rejected with cause; flagged invariant attacks; factual corrections; seat reliability notes — which seats failed, looped, or exceeded the format; open questions for the operator; validation results; verdict) and return the structured ledger object.
13. Process-porn check (the boundary test). For every mechanism in the plan and every accepted addition: running harness code must branch on the artifact (a gate reads it, a ledger query blocks on it, a certificate is verified, a tag transition is refused). A proposal that adds a report, dashboard, matrix, meta-review, scoreboard, or check that no code branches on is REJECTED as ceremony unless it names its consumer, the gate it enforces, the observed defect class that justifies it, and its retirement condition. Prefer deleting a section that earns nothing over adding to it. A proposal about the review apparatus itself (more rounds, more ledgers, more councils) is rejected: the plan is the deliverable.
