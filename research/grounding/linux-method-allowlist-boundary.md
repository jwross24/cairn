## Current enforcement boundary

The pinned `ladder_method` template requires no network egress, declared process backends, scratch-only writes, unrestricted reads, and the `sandbox-exec` mechanism (`bundle/allow_lists.json:4-16`). `allowlist.template` validates those policy fields, and `mechanism_for` maps the only registered mechanism to Darwin and `/usr/bin/sandbox-exec`; an unavailable arm raises `AllowListRefused` (`src/cairn/allowlist.py:38-39,100-132,190-196`). The successful Linux platform-argument refusal reported in bead `cairn-hcl.1` exercises this branch only. It is not evidence of Linux enforcement.

On Darwin, `profile_bytes` expresses deny-default access, permits process forks, permits exec only at literal paths, allows reads under `/`, and allows writes under the supplied scratch path (`src/cairn/allowlist.py:57-65,220-223`). `instantiate` resolves the counted executable and each declared process backend, requires the supplied process paths to match declared process backends exactly, then adds derived interpreter re-exec targets (`src/cairn/allowlist.py:135-155,176-187,225-262`). In-process declarations add no executable path. The framework-Python re-exec target is derived only for the recognized framework layout and non-script interpreter (`src/cairn/allowlist.py:176-187`).

`argv_for` wraps the method command in `sandbox-exec` and checks that `argv[0]` is allow-listed (`src/cairn/allowlist.py:325-330`). `check_binding` re-derives the record from gate-owned launch inputs (`src/cairn/allowlist.py:298-313`), while `check_instantiation` checks internal consistency and a maximum count of executable roots (`src/cairn/allowlist.py:265-295`). The production dispatch path calls only `check_instantiation` on the supplied record (`src/cairn/ladder.py:232-262`). `runner.launch` starts `python -m <skill>` with a scratch argument through `spawn_and_wait`; it does not call `check_binding`, `write_profile`, or `argv_for` (`src/cairn/ladder.py:384-410`; `src/cairn/runner.py:152-153,254-283,441-510`). The repository search for these allow-list operations found no other production caller. The integration file is the OS-contract test path and directly calls `allowlist.argv_for` before invoking the child (`tests/integration/test_ladder_allowlist_enforcement.py:77-80`); this inventory does not establish that the allow-list is applied to production ladder runs.
